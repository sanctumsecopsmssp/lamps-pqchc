PQC Hybrid Commitment (PQCHC) X.509 v3 Extension

Abstract

This document defines the PQC Hybrid Commitment (PQCHC) X.509 v3 extension, a non-critical certificate extension that records a cryptographic commitment to a post-quantum algorithm migration schedule directly in an X.509 certificate. The commitment allows relying parties to verify, at certificate validation time, that the issuing CA has made a binding, verifiable declaration of its PQC migration timeline.¶

This revision (-03) clarifies differentiation from composite-signature schemes (draft-ietf-lamps-pq-composite-sigs, draft-ietf-lamps-cert-binding-for-multi-auth) and adds a Posture B IPR notice. The PQCHC extension encodes a commitment to future algorithm agility — it is not itself a composite signature scheme and does not alter the primary signature algorithm of the certificate.¶

1. Introduction

1.1. Motivation

X.509 certificates today carry no verifiable declaration of the issuing CA's post-quantum migration timeline. Relying parties that require PQC-ready certificate chains have no mechanism to distinguish CAs that have committed to a migration schedule from those that have not, without out-of-band policy documents that are not machine-verifiable at certificate validation time.¶

NIST FIPS 204 (ML-DSA) [FIPS204] and FIPS 205 (SLH-DSA) [FIPS205] define the primary post-quantum digital signature algorithms. The PQCHC extension provides a certificate-embedded, cryptographically bound record of when and how the issuing CA commits to transitioning to these or other NIST-approved PQC algorithms.¶

1.2. Differentiation from Adjacent Work

PQCHC is not a composite-signature scheme. It does not define a new signature algorithm, does not modify the signatureAlgorithm field of the certificate, and does not require dual signing. It is a non-critical v3 extension carrying a structured commitment object. This differentiates it explicitly from:¶

  • draft-ietf-lamps-pq-composite-sigs: Defines a composite public key and composite signature algorithm combining classical and PQC algorithms in a single AlgorithmIdentifier. PQCHC carries no composite signature; it carries a commitment to future migration.¶

  • draft-ietf-lamps-cert-binding-for-multi-auth: Defines certificate binding for multi-algorithm authentication, enabling a relying party to require proof of possession of multiple algorithm-specific keys. PQCHC does not define multi-auth binding; it records a CA's migration commitment as a non-critical extension.¶

The PQCHC extension is complementary to composite-signature and multi-auth binding schemes: a CA may issue a certificate with both a composite signature algorithm and a PQCHC extension, using the PQCHC extension to record the schedule for full PQC-only migration once composite-signature support is established in the relying-party ecosystem.¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals as shown here.¶

Migration Commitment:
A structured, cryptographically signed declaration by a CA specifying the target PQC algorithm family, the planned migration date, and a commitment hash binding the declaration to the certificate.¶
PQCHC Extension:
The X.509 v3 non-critical extension defined in this document carrying a Migration Commitment.¶
Commitment Hash:
A hash binding the Migration Commitment to the certificate's tbsCertificate structure, preventing substitution of the commitment across certificates.¶
Target Algorithm Family:
The NIST-approved PQC algorithm to which the CA commits to migrate, identified by OID. RECOMMENDED values: id-ML-DSA (FIPS 204), id-SLH-DSA (FIPS 205).¶

3. PQCHC Extension Definition

3.1. Object Identifier

The PQCHC extension is identified by the following OID (to be assigned by IANA or designated expert; placeholder used until assignment):¶

id-ce-pqchc OBJECT IDENTIFIER ::= { id-ce TBD }
¶

3.2. Syntax 

PQCHCExtension ::= SEQUENCE {
    version            INTEGER DEFAULT 1,
    targetAlgFamily    AlgorithmIdentifier,
    migrationDate      GeneralizedTime,
    commitmentHash     OCTET STRING,
    commitmentHashAlg  AlgorithmIdentifier,
    issuerSig          BIT STRING OPTIONAL
}
¶
version:
Version of the PQCHC structure. This document defines version 1.¶
targetAlgFamily:
AlgorithmIdentifier identifying the target PQC algorithm. MUST be a NIST-approved PQC algorithm OID per FIPS 204 or FIPS 205.¶
migrationDate:
The date by which the CA commits to complete migration to the target algorithm family for new certificate issuance. MUST be a future date at time of certificate issuance. SHOULD NOT be more than 5 years from the certificate's notBefore date.¶
commitmentHash:
Hash of the DER encoding of the certificate's tbsCertificate structure, computed using the algorithm identified in commitmentHashAlg. Binds the commitment to this specific certificate.¶
commitmentHashAlg:
AlgorithmIdentifier for the hash algorithm used in commitmentHash. MUST be SHA-256 or stronger.¶
issuerSig:
OPTIONAL. A signature over the DER encoding of the remaining PQCHC fields using the CA's private key. When present, allows relying parties to verify the commitment without re-verifying the full certificate chain. MAY use the CA's current (classical) signing key or a PQC signing key.¶

3.3. Criticality

The PQCHC extension MUST be marked non-critical. Relying parties that do not implement PQCHC MUST ignore the extension per [RFC5280] Section 4.2. This ensures backward compatibility with existing certificate validation implementations.¶

4. Relying Party Validation Procedure

A relying party that implements PQCHC validation SHOULD:¶

  1. Locate the PQCHC extension by OID in the certificate's v3 extensions.¶
  2. Verify that commitmentHashAlg is an acceptable hash algorithm.¶
  3. Compute the hash of the certificate's tbsCertificate DER encoding using commitmentHashAlg.¶
  4. Verify that the computed hash equals commitmentHash.¶
  5. If issuerSig is present, verify the signature over the remaining PQCHC fields.¶
  6. Evaluate migrationDate against deployment policy: if the migrationDate has passed without CA migration, the relying party MAY treat the commitment as violated and apply policy-defined consequences (e.g., elevated audit logging, rejection of new certificates from that CA).¶
  7. Evaluate targetAlgFamily against deployment policy to confirm the committed algorithm is acceptable.¶

5. Requirements

REQ-PQCHC-1: Non-Critical Extension. The PQCHC extension MUST be non-critical.¶

REQ-PQCHC-2: NIST-Approved Target Algorithm. The targetAlgFamily MUST identify a NIST-approved PQC signature algorithm.¶

REQ-PQCHC-3: Future Migration Date. The migrationDate MUST be a date after the certificate's notBefore at issuance time.¶

REQ-PQCHC-4: Commitment Hash Binding. The commitmentHash MUST be computed over the DER encoding of the certificate's tbsCertificate.¶

REQ-PQCHC-5: Backward Compatibility. The extension MUST NOT cause validation failure on non-implementing relying parties. The non-critical marking satisfies this requirement.¶

REQ-PQCHC-6: No Composite Signature Alteration. The PQCHC extension MUST NOT alter the signatureAlgorithm field or the primary signature of the certificate. It is informational commitment metadata only.¶

6. Security Considerations

6.1. Commitment Binding Strength

The commitmentHash binds the Migration Commitment to a specific certificate. An attacker who can forge the hash can substitute a different commitment into a certificate. The hash algorithm MUST be SHA-256 or stronger to prevent preimage and collision attacks against the binding. In PQC-capable deployments, SHA-3 (SHAKE256) is RECOMMENDED.¶

6.2. Migration Date Enforcement

The PQCHC extension is informational — it records a commitment but does not enforce it. Enforcement is a matter of relying-party policy and ecosystem governance. Deployments SHOULD define policy consequences for CAs that issue certificates past their committed migrationDate without completing migration, such as CA-audit flags or trust anchor removal procedures.¶

6.3. Classical Signature on Commitment

If issuerSig uses a classical (non-PQC) signing key, the commitment signature provides no quantum resistance. In a post-CRQC environment, the commitment's authenticity would rely solely on the certificate chain validation, not the issuerSig field. CAs operating in high-assurance environments SHOULD sign the commitment with a PQC key even before migrating the primary certificate signature algorithm.¶
